## Actual cause

Production logs show successful HTTP200 searches for `80840050013`, `80600030025` and `80960030024`, with zero exact VMD records. Independent scans of the original DBFs and catalogue queries corroborate the missing records. The catalogue is available and indexed; its spatial index, exact SQL and coordinate transformation are not the cause of those empty results. Searches for independently confirmed source identifiers `01000950030`, `40940020002` and `01000950031` returned209,10 and6 actual VMD records both before and after the UI change.

All three recently searched designations **exist in VZD's official Ropaži KKParcel dataset**, but have no exact matching records in the loaded VMD archive. Diagnostic native-geometry intersection checks also find no VMD polygons intersecting these three official parcels. Those checks are diagnostic only: spatial coincidence is never used to create a cadastral association or return substitute matches.

The loaded archive includes other Ropaži-area records, so these particular parcels must **not** be described as geographically outside coverage. Their area is within the loaded extent envelope. The correct status is “VZD land unit verified; no exact VMD compartments found in this source.” This does not establish that the parcel has no forest. Further VMD source information is needed before any forest compartment can be registered for them.

The UI defects were that the generic unverified message obscured this distinction, the three-step header did not provide working navigation, and initial/partial service-loading failures had no usable retry. For example, account initialization failure could leave cached catalogue metadata without a recovered registration context. These failures are covered by explicit controller tests and now recover without replacing the map or using viewport results.
